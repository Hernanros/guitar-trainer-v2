<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → API (POST /today-song/reroll) | Mobile app sends X-User-ID + X-Timezone-Offset headers. Server MUST NOT trust the client to identify itself as a different user; the reroll marker MUST be inserted with `user_id = X-User-ID` from the dep, never from request body. |
| API → Postgres (reroll INSERT) | The partial-unique index `uq_user_sessions_daily_reroll` is the AUTHORITY on "one reroll per day" — application-layer COUNT-before-INSERT is a legibility short-circuit, not the enforcement point. |
| Postgres → API (marker read-back) | Reading `bank_source` from a marker row requires the same `user_id` filter as the write path. Cross-user marker read would leak another user's reroll signal (low value but zero justification for the leak). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04-01 | Elevation of Privilege / IDOR | POST /api/v1/today-song/reroll | mitigate | Handler MUST derive user_id from `Depends(get_user_id)`, NEVER from request body (no body field for user_id). Reroll INSERT statement binds `:user_id` from the dep. Application code path has no accepted way to specify a different user's UUID. |
| T-03-04-02 | Denial of Service | Repeated reroll POSTs | mitigate | DB partial-unique index enforces one-per-day regardless of client behavior — second INSERT raises IntegrityError mapped to 409 (Postgres level). Application-layer COUNT-before-INSERT reduces DB round-trip for common repeat-tap case; on race, the DB constraint is authoritative. No Sonnet call is made in the reroll path (breakdown is fetched separately). Per-request cost is one SELECT + one INSERT + one selector CTE — bounded, cheap. |
| T-03-04-03 | Tampering | Client-forged 409 | accept | A malicious client that fakes "HTTP 409" locally can only make the button disappear on its own screen — it cannot affect server state. Real 409 comes from the DB, which is the source of truth for `rerolls_left`. Next GET /song-of-day reads the actual marker state, so any client-side spoof self-corrects on refetch. |
| T-03-04-04 | Information Disclosure | Cross-user marker read | mitigate | GET /song-of-day marker-read SELECT MUST filter `WHERE user_id = :user_id AND is_reroll_marker = true AND local_calendar_day = :day`. No path exists in the handler to read another user's marker. |
| T-03-04-05 | Tampering | bank_source spoofing | mitigate | `bank_source` is server-computed by select_today_song, never client-supplied. The reroll INSERT writes the value returned from the selector, and the GET marker-read returns the persisted column verbatim. No request field can influence it. |
| T-03-04-SC | Tampering | npm/pip/cargo installs | mitigate | Zero new packages this plan. `@tanstack/react-query`, `sqlalchemy`, `fastapi` are all installed via Phase 1/2. No slopcheck / legitimacy audit required. Verified: no `pnpm add`, `npm install`, `pip install`, `poetry add` will be executed. |
</threat_model>
