## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Tampering | manual invocation of decay_all_nodes() from an endpoint at attacker's whim | mitigate | No endpoint in Slice D exposes decay_all_nodes; it is only invoked by the scheduler or directly from pytest. To hit it externally an attacker would need code execution. |
| T-04-04-02 | Denial of Service | attacker triggers decay repeatedly, causing UPDATE storm | mitigate | Same as T-04-04-01 — no external trigger. Even if invoked externally, the WHERE predicate limits scope to eligible rows only; on the second immediate call no rows would be eligible (updated_at just changed via last_decayed_at? — NOTE: our UPDATE sets last_decayed_at but NOT updated_at, so re-triggering DOES re-hit the same rows. Consider setting updated_at = now() in the UPDATE to prevent re-decay on the same run cycle. Alternatively, add `AND (last_decayed_at IS NULL OR last_decayed_at < now() - interval '7 days')` to the WHERE predicate for idempotency-within-window.) DECISION: use the `last_decayed_at` guard predicate — safer and preserves updated_at semantics for other logic. Update Task 1 action prose: WHERE clause becomes `WHERE updated_at < now() - interval '7 days' AND mastery > 0 AND (last_decayed_at IS NULL OR last_decayed_at < now() - interval '20 hours')`. The 20-hour cushion accounts for APScheduler catch-up (misfire_grace_time) firing the nightly job as late as 20-23h after the intended 03:00 UTC slot; a shorter 6h window would only protect against same-hour retries and would still allow a second decay within the same 24h day if the scheduler caught up late. |
| T-04-04-03 | Repudiation | user disputes mastery loss without knowing decay happened | mitigate | decay_runs is the audit ledger (D-Claude-decay). Every run inserts a row visible to the developer via psql. Future observability phase can surface via HTTP. |
| T-04-04-04 | Denial of Service | silent scheduler crash stops decay indefinitely | mitigate | Every run writes to decay_runs (both success and failure paths). Developer can query `SELECT * FROM decay_runs ORDER BY started_at DESC LIMIT 5` to verify runs happening. Failure path uses a FRESH session so the audit row lands even if the primary session errored. |
| T-04-04-05 | Information Disclosure | logger.info leaks per-node mastery values in log stream | accept | Only aggregate count logged (`%d nodes decayed`); no per-node data in logs. |
| T-04-04-06 | Race Condition | multi-worker deploy would run decay 2+ times concurrently | accept (documented) | Phase 4 posture is `uvicorn --workers 1` per railway.toml. Scheduler docstring documents that multi-worker requires postgres advisory lock or move to Railway cron plugin. |
| T-04-04-SC | Tampering | apscheduler package supply-chain | mitigate | Already audited in Slice A Package Legitimacy Audit (apscheduler==3.10.4, agronholm, 5M+ weekly downloads, LEGIT). No new packages introduced by this slice. |
</threat_model>
