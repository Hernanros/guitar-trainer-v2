# Phase 4.1: AI Drills — Context

<domain>
## Phase Boundary

Turn the Song of the Day breakdown from a static reference (tab + chords + technique-notes-as-paragraphs) into an actionable practice unit by having the AI teacher emit 2–4 named drills per song, each targeting a specific skill_node with a tempo ladder, repetition count, and success criterion. Drills are rated individually so mastery writes back to a single skill_node per drill — tightening the personalization signal the whole product hinges on.

**Recovers the drills-in-service-of-songs vision** that got dropped between PROJECT.md (line 47 diagnoses V1's "practice and real music siloed" failure) and the pre-2026-09-14 ROADMAP (word "drill" appeared 0 times). Phase 4.1 was inserted after the birdseye product-viability-review flagged this as the "biggest risk" — V2 was songs without drills, mirroring V1's drills without songs.

</domain>

<decisions>
## Implementation Decisions

### Drill authoring model (hybrid, Sonnet-inline)

- Sonnet emits 2–4 drills as part of the **SAME** breakdown response (`GET /api/v1/songs/{id}/breakdown`). NO new endpoint. NO new Sonnet quota category — drills ride the existing `feature='breakdown'` governor budget.
- Cached alongside `tab`, `chords`, `technique_notes` (existing cache-forever contract per D-11 — `breakdown_generated_at IS NOT NULL` means the drills are frozen too).
- Each drill is tagged `song_specific: bool` — Sonnet decides per drill. E.g., for Lenny, Sonnet might emit 2 song-specific ("the b3→3 slide SRV uses in Lenny", "chord-melody attack for Lenny's intro") + 1 foundational ("E♭-shape barre chord voicings, isolated"). Trust Sonnet's editorial judgment — don't force a fixed split.
- Response ordering: drills ordered easiest→hardest (Sonnet convention), rendered top-to-bottom on mobile.

### tab_snippet provenance (canonical shape, Sonnet-composed)

- `tab_snippet` is a canonical exercise SHAPE (chromatic slide, isolated arpeggio, alternate-picking loop) — **NOT** a slice of the main song tab.
- Sonnet composes it fresh per drill as part of the breakdown call. No schema addition to skill_nodes, no seeding job, no hardcoded lookup table.
- Shape stays generic ("play G→G♯ on the G string, hold, release") so the drill exercises the technique without demanding the user knows Lenny's exact bar. Copy (name, `what`, `success_criterion`) is where song-specific framing lives.
- Editorial risk: same class as Task #16 (tuning quality) and Task #18 (sparse skill graph) — Sonnet output fidelity for drill patterns is unproven. Plan should include a small manual eval loop on 3–5 songs before shipping.

### Rep counter behavior (manual tap-to-advance)

- Big **"Done one rep"** button on the focused drill screen. Every tap increments `1/N` where N is the drill's `repetitions` (Sonnet-emitted, per-drill).
- No auto-timer, no fake progress bar. Honest to the "you're at your guitar; the app just tracks that you played" contract.
- After N reps at start_bpm → button changes to "Push to next tempo →" (advances to next step in the tempo ladder). After the final tempo step: "Done — this one unlocked it / Getting closer / Not my tempo skip" (rating).
- Metronome integration DEFERRED to Phase 5 (see below).

### Rating write semantics (Claude's Discretion — planner should validate)

**Locked here:** Per-drill rating writes to `skill_nodes.mastery` for the drill's `target_skill_temp_id` via the SAME deterministic path Phase 3 uses for song ratings (D-05, no LLM in write path). Same 3-choice rating enum (`not_my_tempo` / `getting_closer` / `thats_what_im_looking_for`) — reuse existing `RatingLevel` enum + `submit_rating` server logic; extend `user_sessions` to accept a `drill_id` alongside `song_id`, OR add a `drill_ratings` table alongside `user_sessions`.

**Open for planner to resolve:**
- Does the existing song-level rating (rate the WHOLE song) stay, get replaced by drill-aggregate, or coexist?
- If drill ratings and a song rating both fire the same day, is the mastery write additive (both count), replacement (drill wins), or averaged?
- Recommended default: keep song-level rating for now (backward compat) but scale its mastery write DOWN when drill ratings exist for the same session — drill ratings are the primary signal; song rating becomes a confirmation.

### What stays unchanged

- Existing `Breakdown` fields (`tab`, `chords`, `technique_notes`) unchanged and still render — drills are additive.
- Existing rating endpoint + write path (D-05 deterministic) — extended, not replaced.
- Existing `useBreakdown` hook (from 3c67c77 / quick 260908-01) — drills come in the same response.
- `@governed` cost tracking — drills add to the breakdown call's token count; no new governor feature category needed.

</decisions>

## Reusable Assets

- **`Breakdown` Pydantic model** (`server/app/models/song.py`): add `drills: List[Drill] = []` — default empty for backward compat with existing cached breakdowns. Sonnet `_TOOL_DEF` uses `Breakdown.model_json_schema()`, so the schema picks up the new field automatically.
- **`@governed` decorator** (`server/app/ai/governor.py`): breakdown call is already decorated. Drill emission rides the same call — no new governor wiring.
- **`useBreakdown` hook** (`mobile/src/api/breakdown.ts`): drills arrive in `breakdown.data.drills` — no new fetch hook needed.
- **`useSubmitRating`** (`mobile/src/api/sessions.ts`): pattern to mirror for `useSubmitDrillRating` (same POST shape, add `drill_id` field).
- **`RatingPills` component** (`mobile/src/components/RatingPills.tsx`): reuse for drill rating (same 3-choice enum).
- **`TabNotation` component** (`mobile/src/components/TabNotation.tsx`): renders tab_snippet the same way it renders the main song tab. Tuning label from Task #16 quick task applies automatically.
- **`FletcherLoader` component**: reuse if drill emission adds latency to the initial breakdown call.

## Patterns to follow

- **Deterministic writes only (D-05)**: no LLM in the write path. Drill rating → mastery update via existing sessions logic.
- **@governed cost tracking**: any Sonnet-token addition is automatically tracked via existing decorator.
- **Cache-forever per D-11**: once drills are generated, cache them with the breakdown; regeneration only via admin/curator or cache expiration.
- **Fletcher voice**: sharp, diagnostic, next-step. Never vague. Never punitive. Applies to every drill string (name, what, success_criterion, common_trap).
- **Mobile-safe null-guards**: apply the Grace-B/C pattern (from d42ae4c) — drills[] may be empty on pre-4.1 cached breakdowns; UI must handle absent-drills gracefully (render existing tab/chords/notes normally, hide the DRILLS section entirely).
