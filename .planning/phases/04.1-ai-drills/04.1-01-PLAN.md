<objective>
Slice 1 — Server-side drill emission end-to-end.

Extend the existing Sonnet breakdown call so a single call produces the current Breakdown payload PLUS 2–4 Fletcher-voiced practice drills, each tagged with the exact skill_node UUID it targets. No new endpoint, no new governor category, no schema-changing migration. Backward-compatible with pre-4.1 cached breakdowns (drills default to []).

**Working end-to-end at completion:** A unit test that patches `run_technique_breakdown` to return a Breakdown with 3 drills proves that `GET /api/v1/songs/{id}/breakdown` returns those drills in the JSON payload with correct types. A second test proves a drill referencing a nonexistent skill_node id is silently dropped (not 500) and a warning is logged. A third test proves a Sonnet response with only 1 drill (below min_length=2) triggers Landmine #3 soft-fail: the endpoint returns 200 with drills=[] and logs a warning.

Purpose: this is the foundation slice. Plans 02, 03, 04 all consume the Drill contract and Breakdown.drills field this plan introduces. Landing this first with a full-featured Pydantic model (per-field descriptions, min/max constraints) means downstream slices inherit strong types — no `any`, no drift.

Output: extended Pydantic models (Drill class + Breakdown.drills field with min/max length + target_bpm > start_bpm validator), SYSTEM_PROMPT with the DRILLS block from RESEARCH.md §Q1 (including one BAD/GOOD example to defeat tab-slicing), updated _format_user_message that passes target_skills as {id, name} pairs, breakdowns endpoint post-generation validation loop that drops hallucinated-id drills AND soft-fails Landmine #3 (Sonnet emits <2 or >4 drills), and unit tests for schema constraints + endpoint mocked-Sonnet + soft-fail paths.
