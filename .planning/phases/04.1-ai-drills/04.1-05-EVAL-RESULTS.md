## The failures, with evidence

### L1 — Lenny Drill 1 snippet is a verbatim slice of the main tab

This is the prompt's own BAD example, reproduced exactly.

```
Main tab m5 (12/8): [6/7] [5/9] [4/9] [3/8] [2/8] [1/7] [2/8]
D1 tab_snippet     : [6/7] [5/9] [4/9] [3/8] [2/8] [1/7] [2/8] [3/8]
```

First 7 beats are identical in string, fret, and order — verified by string comparison,
not by eye. One note (`[3/8]`) is appended and the time signature is relabelled 12/8→4/4.
That relabelling is arguably worse than a plain copy: it disguises the lift.

Note *which* drill failed. The two drills that isolate cleanly (D2's two-note slide
`[3/2] [3/3] [3/2] [3/3]`, D3's five-note thumb-and-fingers cell) are the ones whose
mechanics are single-string or single-shape. The drill that got lazy is the **barre**
drill — and the prompt's only GOOD example is a single-string slide. There is no worked
example showing what isolation looks like for a *chord* drill, so Sonnet defaulted to
quoting the song.

### L4 — Lenny Drill 3 names the song while flagged `song_specific: false`

> "...the physical independence between thumb (bass anchor) and fingers (melody) that
> **Lenny's** chord-melody style demands."

`song_specific: False`. The rule is an iff and this violates the reverse direction. The
other 17 drills got this right, so the prompt's framing mostly works — but it's stated
as a semantic judgement ("tag true if the copy references THIS song") rather than a
mechanical one, which leaves exactly this crack.

### L5 — ordering is broken on 3 of 5 songs (and on all 5 by tempo)

Two readings, both reported:

**By mechanical complexity** (what I graded on — a drill is harder if it adds strings,
shapes, chord changes, or rhythmic displacement):

- **Lenny** — D1 is a full six-string barre at position VII; D2 is a two-note slide on
  one string. Hardest drill is placed first.
- **Kashmir** — D1 cycles four voicings across all six strings; D3 is one static shape
  repeated for pure rhythm. Easiest drill is placed third.
- **Wonderwall** — D1 moves through four shapes and D2 is a "cold change"; D3 is a
  single shape struck eight times, described in its own copy as a locked grid. Easiest
  drill is placed third.
- Little Wing and Beat It ramp correctly.

**By tempo** (`start_bpm`/`target_bpm` monotonicity) **all five songs fail**:
Lenny 50→55→45, Kashmir 50→55→60→55, Little Wing 50→45→50→40, Beat It 60→60→55,
Wonderwall 60→55→70→75.

Either way L5 is the weakest gate. The prompt says "Order drills easiest→hardest" and
then never defines difficulty or gives Sonnet a mechanism to check the ordering it
produced. Tempo and complexity actively disagree in this output, which suggests Sonnet
is not using a consistent difficulty notion at all.

## Blocking defect found while running: production timeout is too short

Independent of drill quality, and on its own sufficient to withhold SHIP.

The **first** eval run failed 5/5 with `TimeoutError` and produced zero drills.
This was not an Anthropic outage:

- `run_technique_breakdown(timeout_seconds: float = 30.0)`, doubled once on retry → 90s
  per song. 5 × 90s = 450s; observed run time 453.3s. Exact match.
- A single measured call (Lenny, generous timeout) succeeded in **75.9s**, returning
  8 tab measures and 4 drills.

75.9s sits between the 30s first attempt and the 60s retry. **Every breakdown in
production 503s**, and the cache-forever contract means the failure is on the path users
actually hit. The eval only produced gradeable output after being given a 300s timeout.

**Fix (code, not prompt): raise the `timeout_seconds` default to ≥150s** — ~2× the
measured 76s. This is a one-line change but it is a ship blocker and should be verified
against the slowest song, not Lenny.

## Required prompt changes

Named specifically, per the issue's requirement that a REVISE names its fixes.

1. **L5 — make ordering mechanical and checkable.** Replace the bare "Order drills
   easiest→hardest" with a definition and a rule:
   > Difficulty = number of strings + number of distinct shapes + whether a chord change
   > occurs + whether rhythm is displaced. Drill 1 MUST be the simplest mechanic: one
   > shape, no changes. Each later drill adds **exactly one** dimension. A static
   > single-shape drill must NEVER appear after a drill containing a chord change.

   Also resolve the tempo contradiction explicitly — either require `start_bpm` and
   `target_bpm` to be non-decreasing across drills, or state that tempo is not the
   difficulty signal. Right now the prompt implies the first and the output does neither.

2. **L1 — add a self-check and a chord-drill GOOD example.** Append to the `tab_snippet`
   block:
   > Before emitting `tab_snippet`, compare it against the main tab you just wrote. If
   > any 3 consecutive beats match the string/fret sequence of any main-tab measure, the
   > snippet is a slice — rewrite it.

   And add the missing worked example, since the existing GOOD case only covers a
   single-string ornament:
   > GOOD (chord drill): for a barre or voicing drill, play the shape alone on two or
   > three strings, or hold it and drill only the attack — never quote the song's
   > measure containing that chord.

3. **L4 — restate as a mechanical test.** Replace the judgement-based phrasing with:
   > If `what` mentions the song title or the artist anywhere, `song_specific` MUST be
   > true. If you intend a foundational drill, do not mention the song or artist in
   > `what` at all.

mechanism. That is a fixable prompt problem, not a model-capability problem.

## Eval-harness bugs fixed to make this run possible

The script could not have produced a valid 30-gate table as written. All fixes are in
`server/scripts/eval_drills.py`, each marked `EVAL FIX (2026-09-15)`.

1. **Governor cap would have silently truncated the eval to 3 songs.**
   `run_technique_breakdown` is `@governed(feature='breakdown', cap=3, window='7d')`, but
   the script seeded **one** throwaway user for all 5 songs. Songs 4–5 would raise
   `BudgetExceededError`, land in the error list, and leave 12 of 30 gates ungradeable.
   Fixed: one throwaway user per song. The cap is a production spend control, not a
   property of drill quality, so bypassing it is faithful to what this eval measures.

2. **The summary would have crashed after all five paid calls.** `_query_total_tokens`
   selected `actual_input_tokens` / `actual_output_tokens`; the real columns (migration
   0004) are `prompt_tokens_actual` / `output_tokens_actual`. `UndefinedColumn` would
   raise in the `finally` block — after the money was spent. Fixed, and `dollars_actual`
   is now reported.

3. **L1 was structurally ungradeable.** The script printed drill snippets but never the
   main song tab, so "is this snippet a slice of the main tab" could not be checked at
   all. Fixed: the main tab is printed in a compact `m1: [6/3 5/5] [4/7]` form alongside
   each snippet. **This fix is what caught the Lenny L1 failure** — it was invisible in
   the original output format.

4. Timeout made configurable via `EVAL_TIMEOUT_SECONDS` (default 300) so quality can be
   measured at all. This is a harness setting and deliberately does **not** paper over
   the production default, which is reported above as a blocking defect.
