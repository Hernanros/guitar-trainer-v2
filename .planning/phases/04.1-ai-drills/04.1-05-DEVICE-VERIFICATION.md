### Why the rebuild — SPENT, 2026-09-16

The `0db7955` pair was superseded. **Item 2 would have failed at ~60s on those builds for a
client-side reason that has nothing to do with the server.**

FLE-29 (`12c63fb`) landed after the server fixes and is a **mobile** fix. On iOS, RN's fetch is the
whatwg-fetch polyfill: it registers `xhr.ontimeout` but never assigns `xhr.timeout`, so the native
request keeps `defaultSessionConfiguration`'s **60s** `timeoutIntervalForRequest` — below the
**72.1s** a real breakdown takes. The symptom is easy to misfile: the first tap fails at ~60s while
the server succeeds at ~75s and caches it, the second tap succeeds instantly from cache, and **two of
the three weekly quota units are already spent**. That looks like an item-2 failure plus an item-5
quota anomaly when it is one client bug. `apiFetch` now routes the breakdown call through
XMLHttpRequest with an explicit 240s timeout — above the server's 150s ceiling on purpose, so the
server's structured error is what the user sees rather than a client abort. Android was unaffected
(OkHttp defaults to no timeout).

All three commits the walk needed are **confirmed present** in `3521d41` (verified with
`git merge-base --is-ancestor`, not assumed):

| Commit | In build | Why it had to be there |
|---|---|---|
| `12c63fb` FLE-29 | yes | **Required for item 2.** Without it iOS aborts at 60s and burns quota doing it. |
| `19de9c0` FLE-5 | yes | Metronome engine + tempo ladders — needed for the metronome hold-tempo check. |
| `c58f6d4` FLE-27 | yes | expo-updates. Later mobile-only fixes can now ship OTA without EAS quota. |
| `3521d41` FLE-5 | yes | Click assets + injected-module audio emitter — the metronome's actual sound. |

## Pre-flight against production — run 2026-09-16, no hardware

Before handing the walk over, the server half of items 1, 3 and 4 was exercised end-to-end against
**production** with a throwaway user (`0efdb6d8-daf3-4be5-95dd-08ea0cecd93b`), so the human does not
burn walk time — or two calendar days — discovering a server bug. **This does not close any item.**
Every item below still needs its on-device UI half; what is closed is the question "will the server
even let this happen".

**How "Day 2" was reached without waiting a day.** The server computes the local calendar day itself
from `X-Timezone-Offset` (`deps.py:47`, valid range ±840 min). At 11:09 UTC, `X-Timezone-Offset: 840`
resolves to local day **2026-09-17**. Same code path as a real second day — day-keyed rotation,
idempotency and reroll markers all read that computed day. It is not a clock hack in the DB.

|---|---|---|

| Day 1 | `GET /song-of-day` (tz 0) | **200** in 0.48s — song **91 "Little Wing"**, `from_bank:false`, `breakdown_quota:{remaining:3,cap:3}` |

| Reroll ×2 | `POST /today-song/reroll` (tz 840) | **409** `"Already used today's reroll."` |

**What this buys each item**

  local day returned a *different* song. The device half is now only "does the UI show it".
- **Item 4** — `bank_source: "user_bench"` is reachable and reproducible (rate the working_on pick,

  `seed_catalog` variant was not reached.

**Two findings the walk should expect**

1. **Item 3's stated pass criterion may not hold.** The reroll returned **the same song** (92) it
   replaced, and `rerolls_left` still went to 0. With only 4 user songs that is plausible — the
   reroll re-seeds the same 75/25 CTE rather than excluding the current pick — but "tap → song
   changes" is then not guaranteed. **Do not auto-fail item 3 on an unchanged song.** Record the
   song ids before and after, and mark the *button* behaviour (hides, `rerolls_left=0`, no button on
   re-open) separately from the *song-changed* behaviour.
2. **`from_bank` disagrees between two endpoints for the same state.** `POST /today-song/reroll`
   answered `from_bank:true, bank_source:null`; an immediate `GET /song-of-day` for that exact state
   answered `from_bank:false, bank_source:null`. `song_of_day.py`'s reroll-marker branch carries a
   comment about deliberately replacing a hard-coded `from_bank=True` with
   `from_bank = bank_source is not None` — that fix is on the **GET** branch only; the **POST**
   response still reports the old value. User-visible impact today is nil, because the client guards
   with `Boolean(from_bank && bank_source)` — the chip hides either way. But the chip is only correct
   because the client compensates for a server inconsistency. Filed as **FLE-41**, not fixed here: a
   server change mid-walk would invalidate what the walk observes. FLE-41 also carries finding 1
   above, since both are decisions about the same reroll path.

**Deliberately not pre-flighted:** items 2, 5, 6 and 7a–o. All need real Sonnet breakdowns, which
are capped at 3 per 7 days *per user*. Spending them from curl would leave the walk without quota.
They were left untouched on purpose. (The throwaway user above is a separate UUID, so **no quota was
consumed on Hernan's device user**.)

**One correction to the "cold-start 500 CLEARED" claim above.** It is cleared for the real app flow,
but the evidence behind it was pre-seeded users (`dddddddd-…-fe88/fe99`, in the `users` table before
the request). A genuinely unseen UUID calling `GET /song-of-day` *without onboarding first* still
500s — `songs_user_id_fkey` FK violation inside `_ensure_catalog_song_as_user_song`, not the old
`Decimal` bug. **This is not a walk blocker:** the app mints the UUID, sees `onboarded_at` null,
routes to `/onboarding`, and `POST /users` creates the row before Today is ever reached — and the
Settings "Start over?" reset keeps the UUID and re-runs onboarding, so it never takes the bare path
either. It is only reachable by curl, or by an app that somehow lands on Today with onboarding
failed. Worth knowing, because the symptom is an opaque `Internal Server Error` with no structured body.
