### Why the rebuild — SPENT, 2026-09-16

The `0db7955` pair was superseded. **Item 2 would have failed at ~60s on those builds for a
client-side reason that has nothing to do with the server.**

FLE-29 (`12c63fb`) landed after the server fixes and is a **mobile** fix. On iOS, RN's fetch is the
whatwg-fetch polyfill: it registers `xhr.ontimeout` but never assigns `xhr.timeout`, so the native
request keeps `defaultSessionConfiguration`'s **60s** `timeoutIntervalForRequest` — below the
**72.1s** a real breakdown takes. The symptom is easy to misfile: the first tap fails at ~60s while
the server succeeds at ~75s and caches it, the second tap succeeds instantly from cache, and **two of
the three weekly quota units are already spent**. That looks like an item-2 failure plus an item-5
quota anomaly when it is one client bug. `apiFetch` now routes the breakdown call through
XMLHttpRequest with an explicit 240s timeout — above the server's 150s ceiling on purpose, so the
server's structured error is what the user sees rather than a client abort. Android was unaffected
(OkHttp defaults to no timeout).

All three commits the walk needed are **confirmed present** in `3521d41` (verified with
`git merge-base --is-ancestor`, not assumed):
