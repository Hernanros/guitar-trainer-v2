### Why the rebuild — SPENT, 2026-09-16

The `0db7955` pair was superseded. **Item 2 would have failed at ~60s on those builds for a
client-side reason that has nothing to do with the server.**

FLE-29 (`12c63fb`) landed after the server fixes and is a **mobile** fix. On iOS, RN's fetch is the
whatwg-fetch polyfill: it registers `xhr.ontimeout` but never assigns `xhr.timeout`, so the native
request keeps `defaultSessionConfiguration`'s **60s** `timeoutIntervalForRequest` — below the
**72.1s** a real breakdown takes. The symptom is easy to misfile: the first tap fails at ~60s while
the server succeeds at ~75s and caches it, the second tap succeeds instantly from cache, and **two of
the three weekly quota units are already spent**. That looks like an item-2 failure plus an item-5
quota anomaly when it is one client bug. `apiFetch` now routes the breakdown call through
XMLHttpRequest with an explicit 240s timeout — above the server's 150s ceiling on purpose, so the
server's structured error is what the user sees rather than a client abort. Android was unaffected
(OkHttp defaults to no timeout).

All three commits the walk needed are **confirmed present** in `3521d41` (verified with
`git merge-base --is-ancestor`, not assumed):

### A defect this pre-flight caught, fixed before the build — mic permissions

`app.json` listed the plugin bare, as `"expo-audio"`, which takes its defaults. Generating the native
projects shows what those defaults actually ship:

- **Android** — `android.permission.RECORD_AUDIO`, a *dangerous* runtime permission
- **iOS** — `NSMicrophoneUsageDescription = "Allow Fletcher to access your microphone"`

For an app that never records, whose two audio files total 6 KB, and whose **locked MVP scope says
"no mic"**. A pilot tester sideloading the APK would have seen "Record audio" in the app's
permissions; on the TestFlight path (FLE-34) an unjustified mic string is a review risk. Verified
against the installed plugin (`node_modules/expo-audio/plugin/build/withAudio.js`) and the v57 docs —
`recordAudioAndroid` and `microphonePermission` both default to on.

Fixed by configuring the plugin explicitly, so no property is an inherited default:

```json
["expo-audio", {
  "microphonePermission": false,
  "recordAudioAndroid": false,
  "enableBackgroundRecording": false,
  "enableBackgroundPlayback": true
}]
```

Re-generated and confirmed: `RECORD_AUDIO` gone from `AndroidManifest.xml`,
`NSMicrophoneUsageDescription` gone from `Info.plist`.

**`enableBackgroundPlayback` is deliberately kept `true`** — that is a decision, not the default
slipping through. It is what lets the click survive a screen lock, which is the normal case for a
phone propped on a music stand, and it is what makes the screen-lock note above answerable. It
carries a visible cost worth knowing before the walk: `UIBackgroundModes: [audio]` on iOS,
`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` plus an `AudioControlsService` on Android.
**Expect lock-screen / notification media controls for a metronome** — note how that behaves, it may
want suppressing later, but it is not a failure of the audio itself.

### FLE-5 D9, 2026-09-16 — the app now measures its own timing, so read the numbers

**Replaces the "second metronome app" method above.** Do not phase-compare two apps by ear. They are
started by hand, so they begin up to a beat apart, and the reference app has its own jitter — the
instrument was less precise than the thing being measured. Worse, a "fail" from it is unactionable,
because the three ways this can break all sound the same:

| What you hear | What it actually is | Whose problem |
|---|---|---|
| Slowly slides out of phase | Accumulated grid error | Scheduler bug — a real defect |
| Beats wobble, phase holds | Per-beat JS-thread jitter | Expected; the question is how much |
| Click stops, then resumes | The OS suspended the app | Wake lock / background audio |

The engine has been computing the exact figure per beat since its first commit; nothing displayed
it. Now it does.

**How to open it: long press the tempo readout** (the "120 BPM / From this drill" block on the right
of the metronome card). Hidden by default so the drill screen stays a drill screen. Long press
again to close. Two lines appear:

```
2:31 · 302 beats · grid +4ms · jitter max 18ms / avg +5ms · 0 skipped · 0 dropped
max jitter 3.6% of a beat
```

**What each number means, and what fails:**

| Field | Reading | Fail looks like |
|---|---|---|
| `grid` | Where the latest beat sits against `anchor + n × interval`. **This is the "holds tempo" number.** It does NOT accumulate — it should look the same at 45 minutes as at 30 seconds. | Growing steadily with time. A grid of ±20ms at 45 min is a pass; ±4000ms is the scheduler failing. |
| `jitter max` / `max jitter % of a beat` | Worst single beat. This is what the hardware is *for* — no laptop can measure it. | Record it regardless. Under ~1% of a beat is inaudible to anyone; if it is audible, the percentage is the number to report. |
| `skipped` | Beats the grid contained that the device never fired — counted from gaps in the beat index. **Non-zero means the app was suspended or the JS thread stalled**, not that timing is bad. | Any non-zero value during a run where the screen stayed on. 30s of iOS auto-lock reads as ~59 skipped at 120 BPM. |
| `dropped` | Clicks swallowed for arriving more than half a beat late, so they were not played out of position. | A handful over 45 min is the design working. Dozens means the thread is badly contended. |
| run clock / beats | Sanity check that it ran as long as you think. | — |

**Reset behaviour, so you do not mismeasure:** the counters reset every time you press **Start
click**, and are *retained* after **Stop click**. So the procedure is: start, leave it 45 minutes,
stop, then read. A stray tap mid-walk restarts the measurement — if that happens, note it and
restart the sitting.

A tempo-ladder push does **not** reset the counters and does **not** count as skipped beats, so
walking a ladder mid-run is fine and is worth doing (it is the D2 re-anchor path).

- [ ] `grid` at the end of the run: ____________  (and: did it grow over the run? Y / N)
- [ ] `jitter max`: ______ ms = ______ % of a beat
- [ ] `skipped`: ______   `dropped`: ______
- [ ] Run clock at stop: ______   Beats: ______

**This readout arrived after the `b2499a6` builds were cut.** It is JS-only — the native fingerprint
is byte-identical (iOS `4d91c7cb…`, Android `5400fef0…`), verified with
`expo-updates fingerprint:generate` — so it reaches those same binaries over `eas update` with **no
