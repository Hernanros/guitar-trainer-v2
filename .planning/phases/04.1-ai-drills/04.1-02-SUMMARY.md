# Phase 04.1 Plan 02: Server per-drill rating write path Summary

**One-liner:** Server-side drill rating write path — Alembic 0005 extends user_sessions with drill_index + target_skill_node_id + COALESCE-based partial-unique index; submit_rating gains a drill branch that writes mastery to exactly one skill_node with T-04.1-05 defense-in-depth; drill-primary 409 aggregation policy blocks song ratings after drills; and GET /api/v1/songs/{id}/breakdown now returns BreakdownEnvelope with server-computed drill_rated_today_indices (B1 fix) as the durable source of truth for mobile drill-primary UI state.

## Migration Details

**Filename:** `server/alembic/versions/0005_user_sessions_drill_columns.py`
**Revision id:** `0005`
**Down-revision:** `0004`

**Schema changes:**

| Change | Name | Details |
|---|---|---|

| ADD COLUMN | `user_sessions.target_skill_node_id` | UUID NULL, FK `skill_nodes.id` |

| ADD CONSTRAINT | `ck_drill_index_pairs_skill_node` | CHECK: `(drill_index IS NULL AND target_skill_node_id IS NULL) OR (drill_index IS NOT NULL AND target_skill_node_id IS NOT NULL)` |

**Downgrade:** DROP CHECK → DROP recreated index → CREATE original index (from 0003 shape, no drill_index in key) → DROP target_skill_node_id column → DROP drill_index column. Verified round-trip clean on a fresh DB. Downgrade is expected to fail on a DB that already has multiple drill ratings per (user, song, day) — that's correct behavior: cannot downgrade to a schema that can't represent the data.

## COALESCE partial-index approach — CHOSEN over fallback

RESEARCH.md landmine #4 warned that if Postgres rejected `COALESCE(drill_index, -1)` in a partial-unique index, we'd need to fall back to two separate partial indexes (one for `drill_index IS NULL`, one for `drill_index IS NOT NULL`). **The COALESCE approach worked on Postgres 15 (Railway default) — fallback not needed.** Verified by:
- `test_0005_partial_unique_index_still_named_correctly` — asserts recreated index name AND that `COALESCE` appears in its `indexdef`.
- Multiple downgrade → upgrade cycles executed cleanly on a fresh DB.
- Live smoke: three coexisting rows for the same (user, song, day) — one with drill_index=NULL, one with drill_index=0, one with drill_index=1 — all succeed; duplicate drill_index=0 correctly 409s.

## Deviations from Plan

### Neutral — Task 4 test count drift (added 1 extra envelope test)

Plan said "7 tests" in Task 4 behavior list. I shipped 8 by splitting the round-trip check: the plan's `test_breakdown_envelope_shape` test asserted `model_dump_json` → `model_validate_json` round-trip cleanly for the envelope. But when the wrapped Breakdown has `drills=[]` (default), `model_dump_json` serializes drills explicitly, and re-validation trips `Breakdown.drills` `min_length=2`. That's the same Wave 1 landmine that motivated the `_load_cached_breakdown` helper — the envelope wrapper does not (and should not) change that invariant.

Split the round-trip check into two tests:
- `test_breakdown_envelope_shape`: asserts envelope construction + `model_dump()` shape (works with drills=[]) — no JSON round-trip.
- `test_breakdown_envelope_json_roundtrip_with_drills` (NEW): asserts `model_dump_json` → `model_validate_json` round-trip works when drills are present (2+ items). This is the realistic production path — when the endpoint returns an envelope for a real breakdown with drills, JSON round-trip works cleanly.

Coverage identical to plan; assertion boundaries cleaner. Not a functional deviation.

## Handoff Notes

### For Plan 04.1-03 (mobile — currently running in parallel; already partially landed)

- `GET /api/v1/songs/{id}/breakdown` **response shape has changed** to `BreakdownEnvelope { breakdown: Breakdown, drill_rated_today_indices: number[] }`. Mobile consumers must access `envelope.breakdown.drills`, `envelope.breakdown.tab`, etc. instead of `response.drills`, `response.tab`.
- The regenerated `mobile/src/schema.d.ts` (Plan 03 commit `450be50`) already reflects this shape. Plan 03's `useBreakdown` hook (Plan 03 commit `749315c`, `mobile/src/api/breakdown.ts`) now returns `BreakdownEnvelope` — consuming components need `const bd = envelope.breakdown;` or similar destructure.
- `envelope.drill_rated_today_indices: number[]` is the **durable server-derived source of truth** for the drill-primary UI state. Every render of the breakdown screen has access to this list — no QueryClient subscription pattern needed to detect "did the user just rate a drill?".

### For Plan 04.1-04 (mobile drill-detail screen)

- **POST to `/api/v1/sessions` with `{song_id, rating, drill_index, target_skill_node_id}`** to submit a drill rating. `drill_index` is the 0-based position of the drill in `envelope.breakdown.drills` (already validated Sonnet-side by Wave 1's endpoint filter, so the UUID in `drill.target_skill_temp_id` is guaranteed to be a real skill_node UUID owned by the current user). Send both fields together — sending only one returns 422 from `SessionCreate._drill_pair_both_or_neither`.
- **Consume `envelope.drill_rated_today_indices`** for the drill-primary UI: for each drill card, check `envelope.drill_rated_today_indices.includes(drillIndex)`. If true, render the drill as "rated" and disable the rating pills. Because this list is server-computed and returned on every GET, it survives app restart, cache invalidation, and cross-component navigation.
- **Song-level RatingPills**: if `envelope.drill_rated_today_indices.length > 0`, disable the whole-song RatingPills with copy like "Rate the drills you did — the whole-song rating is off after drills." (Server also enforces via 409 `SONG_RATING_BLOCKED_BY_DRILL` — client-side check is UX polish, server-side is the guardrail.)
- **409 handling on POST /api/v1/sessions:**
  - `detail` containing `SONG_RATING_BLOCKED_BY_DRILL` → user tried a whole-song rating after drills. Show a Fletcher-voiced toast and disable the pill.
  - `detail = "Already rated this drill today."` → duplicate drill_index for same day. Show "You already rated this drill today" toast.
  - `detail = "Already rated this song today."` → duplicate whole-song rating for same day (pre-existing behavior).

### For future admin-regen tool

Recording the RESEARCH.md landmine #7 concern here so it doesn't get lost: if an admin regenerates a breakdown (invalidating `songs.breakdown_generated_at` and calling Sonnet again) AFTER the user has already rated drills 0-2, Sonnet may re-order drills — so `drill_index=2` might refer to a different drill in the new emission. Cache-forever (D-11) currently prevents this in prod. Any admin-regen tool must either (a) invalidate existing user_sessions drill_ratings for the affected song at regen time, or (b) block regen when drill_ratings exist for the song.
