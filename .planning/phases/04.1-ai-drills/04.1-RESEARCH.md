## Executive Summary

- **Sonnet's tool_use schema handles nested `list[Drill]` fine** (Pydantic `Breakdown.model_json_schema()` picks it up automatically — no schema flattening needed, already proven by Phase 2's `SonnetOnboardingOutput` and Phase 3's `Breakdown`). The reliability problem is not the schema — it's the **prompt discipline** to get `song_specific: bool` tagged correctly and to prevent Sonnet from lazily slicing the main tab into `tab_snippet`. Recommend field-level constraints in the schema `description` fields + one negative example in the SYSTEM_PROMPT.
- **Storage shape recommendation: EXTEND `user_sessions`** with two nullable columns (`drill_index INT` + `target_skill_node_id UUID`). Rationale: reuses the existing atomic write path, existing partial-unique idempotency indexes, existing `RatingLevel` enum, and existing 409 semantics. A new `drill_ratings` table doubles the write surface for no schema benefit (drill ratings ARE session ratings — just with sub-song granularity).
- **Aggregation policy recommendation: "Drill-primary, song-optional, no double-count"** — if any drill for song X was rated today, the song-level rating is disabled in the UI (grayed out with "Rate the drills you did — the whole song is optional after that"). Enforce server-side with a CHECK/precondition. Simplest deterministic write model; matches CONTEXT.md's preferred default without introducing scaling factors. See §Q3 for the alternatives table.
- **Cost impact is negligible.** Adding 2–4 drills (~700–1,400 output tokens worst case) adds **~$0.011–$0.021 per breakdown call**. At 3 breakdowns/user/week × 1 user × 4.3 weeks = ~13 breakdowns/mo → **~$0.14–$0.27/mo extra**. Well inside the $20/mo cap. The @governed cap of 3/user/7d is already the load-bearing spend control; drills don't change the math.
- **Precedent: Yousician "phrase loops", Fender Play "short repeating drills", TrueFire "loop until you nail it"** — all four competitors already frame per-song exercises as loop-a-hard-section + rate. Phase 4.1 lands squarely in industry-standard framing. Naming should lean on words guitar players already recognize: *loop*, *drill*, *phrase*, *pass* — CONTEXT.md's rep-counter "Done one rep" is on-voice.

**Primary recommendation:** Ship as a single migration (0005) that adds two nullable columns to `user_sessions`, extend the Pydantic `Breakdown` model with a `drills: list[Drill] = []` field (default empty for backward compat), add the drill emission block + one negative example to `SYSTEM_PROMPT`, and gate the plan with a manual-eval verification wave on 3 songs before user-facing rollout.

## Q1 — Sonnet prompt engineering for hybrid drills

### The schema side is easy

Anthropic's tool_use supports standard JSON Schema including `type: array` of nested `type: object`, `enum`, `const`, `required`, and `$ref`/`$defs` — the same $defs/$ref pattern that `Breakdown.model_json_schema()` already emits and that Task 1's Phase 3 spike confirmed works ([Anthropic structured outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [Nested object extraction](https://theneuralbase.com/anthropic-api/learn/intermediate/nested-object-extraction/)). Two limits worth noting:

- **No recursive schemas.** `Drill` referencing itself (children-drills) would fail. Not a concern for 4.1 — drills are flat.
- **`required` at the object level matters.** If you don't mark `song_specific`, `target_skill_temp_id`, `start_bpm`, `target_bpm`, `repetitions`, `success_criterion` as required, Sonnet may silently omit them. Pydantic v2 non-`Optional` fields do the right thing when `model_json_schema()` runs — verify the emitted schema has `"required": [...]` populated for the Drill sub-model.

### The reliability side is prompt discipline

Anthropic's guidance on tool-use reliability is consistent across three official sources ([Prompting best practices](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices), [Prompt engineering overview](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview), [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)):

1. **Precise `description` fields on schema properties dramatically reduce malformed calls.** For `tab_snippet` and `song_specific`, do the enforcement *at the schema description level*, not just in the SYSTEM_PROMPT. The tool schema description is preserved verbatim in the tool call.
2. **Claude Sonnet interprets prompts literally.** Vague "should be specific" language underperforms explicit constraints ("Between 2 and 4 items. Each drill's `tab_snippet.measures` MUST have 1 or 2 measures, no more."). Use ranges.
3. **One negative example beats three positive ones for constraint enforcement.** For the "don't slice the main tab" rule, include: *"BAD: `tab_snippet` copies measures 3-4 from the main tab. GOOD: `tab_snippet` isolates just the chromatic slide from beats 2-3 of measure 3, played on the G string alone."*

### Recommended prompt additions

Add this block to `SYSTEM_PROMPT` in `server/app/ai/breakdown.py` after the TUNING block (around line 94):

```
DRILLS (produce 2-4):
After the main tab/chords/technique_notes, emit 2-4 short practice drills.
Each drill isolates ONE skill from the target_skills list and must be
playable in under 60 seconds per rep.

For each drill, tag `song_specific: true` if the drill's `what` copy
explicitly references THIS song (e.g., "the b3→3 slide SRV uses in Lenny's
intro"). Tag `song_specific: false` if the drill is a foundational
technique any guitarist could benefit from regardless of song context
(e.g., "isolate the E-shape barre chord in position VII").

For `tab_snippet`: compose a CANONICAL EXERCISE SHAPE that isolates the
technique. DO NOT copy a slice of the main song tab. The snippet should
be 1-2 measures maximum and exercise ONE mechanic per drill.

BAD: `tab_snippet` is measures 3-4 from the main song tab.
GOOD: `tab_snippet` is just the two-note slide on one string, played
      alone, no bass, no chord — isolated so the user drills the mechanic
      not the song.

Order drills easiest→hardest. Start_bpm should be a comfortable warmup
tempo, target_bpm should be a stretch (10-40 BPM higher, in 5-BPM
increments to match the skill graph's 5-bpm bins). Repetitions: 8-30
per tempo step.
```

Also add per-field enforcement in the Drill Pydantic model docstrings (which Pydantic surfaces as schema `description` — Sonnet respects these):

```python
class Drill(BaseModel):
    name: str = Field(..., description="Short imperative name, e.g., 'Isolate the b3→3 slide'. Fletcher voice: sharp, diagnostic.")
    target_skill_temp_id: str = Field(..., description="The single skill_temp_id from target_skills this drill exercises. Exactly one.")
    song_specific: bool = Field(..., description="True if `what` copy names this song. False if the drill is a foundational technique any guitarist could use.")
    what: str = Field(..., description="1-2 sentences explaining what the user does. If song_specific=true, name the song and the moment.")
    tab_snippet: Tab = Field(..., description="Canonical exercise shape. 1-2 measures max. MUST NOT be a slice of the main song tab.")
    start_bpm: int = Field(..., ge=40, le=180, description="Warmup tempo. Multiple of 5.")
    target_bpm: int = Field(..., ge=40, le=220, description="Stretch tempo. Multiple of 5. Between 10-40 BPM higher than start_bpm.")
    repetitions: int = Field(..., ge=8, le=30, description="Reps per tempo step.")
    success_criterion: str = Field(..., description="One sentence — what 'unlocked' sounds like. Fletcher voice.")
    common_trap: Optional[str] = Field(None, description="Optional. One sentence about the mistake beginners make on this mechanic.")
```

**Landmines to avoid:**

- **Don't put the drills as a *separate* tool call.** Force-tool-choice already binds Sonnet to `emit_breakdown` — add drills INSIDE that tool's schema so they land in the same tool_use block. Two tool calls doubles round-trip cost and complicates the count_tokens estimate.
- **Don't rely on `min_items: 2, max_items: 4` alone.** JSON Schema `minItems`/`maxItems` are honored by Sonnet, but they don't guarantee semantic diversity — Sonnet can emit 4 near-identical drills. The SYSTEM_PROMPT's "easiest→hardest" and per-drill `target_skill_temp_id` constraint is what forces diversity.
- **Don't let `target_skill_temp_id` be free-form.** Pass the target_skill_temp_ids list in the user message (mirroring `target_skill_names` already there) and add: *"target_skill_temp_id MUST be one of the ids provided in the user message. Do not invent new ids."* Otherwise Sonnet will hallucinate slugs.

Confidence: **MEDIUM-HIGH**. Schema mechanics are verified (Phase 2 + Phase 3 in-repo precedent). Prompt-side reliability is verified via Anthropic official docs but ultimate quality is unproven — this is where the CONTEXT.md manual-eval-loop-on-3-5-songs mandate earns its keep.

## Q2 — `drill_ratings` schema shape

### Option A — new `drill_ratings` table

Pros:
- Clean separation; song ratings and drill ratings never overlap.
- Easy to query "all drill ratings for skill X" (no `WHERE drill_index IS NOT NULL` filter).

Cons:
- Doubles the write surface: two INSERT paths, two idempotency-index designs, two 409 code paths.
- Doubles the read surface for "did user rate anything today?" queries.
- New table → new Alembic migration + new ORM class + new Pydantic model + new endpoint (or a router param).
- Duplicates the RatingLevel enum reference.

### Option B — EXTEND `user_sessions` with nullable `drill_index` + `target_skill_node_id` (RECOMMENDED)

Pros:
- **Reuses the existing atomic write path** in `server/app/api/v1/sessions.py`. The `submit_rating` handler already does: SELECT-song-owned-by-user → check-idempotency → INSERT session → UPDATE mastery on affected skill_nodes. Extending it to "if `drill_index` is present, UPDATE only the specific `target_skill_node_id`; otherwise UPDATE all song-attached skill_nodes" is a 4-line branch.
- **Reuses existing partial-unique indexes.** The current `uq_user_sessions_daily_rating (user_id, song_id, local_calendar_day) WHERE is_reroll_marker=false` needs a small change (see below) but the pattern is proven.
- **Reuses existing `RatingLevel` enum**, existing `RATING_SHIFTS` dict, existing 409 semantics.
- **No new ORM class, no new Pydantic model, no new endpoint** — just add optional fields to `SessionCreate`.
- Symmetric with how `is_reroll_marker` was added — precedent set by Phase 3 gap-closure.

Cons:
- `user_sessions` now has multi-purpose rows (rating, reroll marker, drill rating). Comment discipline required in the ORM model.
- Idempotency index needs updating to include `drill_index` — see migration shape below.

### RECOMMENDED: Option B

**Migration 0005 shape:**

```python
# Add nullable columns
op.add_column("user_sessions", sa.Column("drill_index", sa.Integer(), nullable=True))
op.add_column("user_sessions", sa.Column("target_skill_node_id", PGUUID(as_uuid=True),
              sa.ForeignKey("skill_nodes.id"), nullable=True))

# Existing partial-unique index needs to gain drill_index in the key
# so multiple drill ratings for the same (user, song, day) don't 409 each other,
# while still preventing the SAME drill_index being re-rated on the same day.
op.execute("DROP INDEX IF EXISTS uq_user_sessions_daily_rating")
op.execute("""
    CREATE UNIQUE INDEX uq_user_sessions_daily_rating
    ON user_sessions (user_id, song_id, local_calendar_day, COALESCE(drill_index, -1))
    WHERE is_reroll_marker = false
""")

# CHECK constraint: if drill_index is present, target_skill_node_id must also be present
op.execute("""
    ALTER TABLE user_sessions ADD CONSTRAINT ck_drill_index_pairs_skill_node
    CHECK ((drill_index IS NULL AND target_skill_node_id IS NULL)
        OR (drill_index IS NOT NULL AND target_skill_node_id IS NOT NULL))
""")
```

`COALESCE(drill_index, -1)` in the unique index treats the whole-song rating (drill_index=NULL) as its own "slot" that can coexist with drill_index=0,1,2,3 rows — but only ONE whole-song rating and only ONE row per drill_index per day. This is the idempotency guarantee.

**Server extension in `sessions.py`:**

```python
# In submit_rating handler, after computing shift:
if body.drill_index is not None:
    # Drill rating: UPDATE only the specific target_skill_node_id
    await db.execute(
        update(SkillNode)
        .where(
            SkillNode.id == body.target_skill_node_id,
            SkillNode.user_id == user_id,  # defense-in-depth per T-03-03-01
        )
        .values(mastery=..., updated_at=func.now())
    )
else:
    # Song rating: existing path — UPDATE all song_skills
    await db.execute(update(SkillNode).where(...).values(...))
```

**Pydantic extension:**

```python
class SessionCreate(BaseModel):
    song_id: int
    rating: RatingLiteral
    drill_index: Optional[int] = None
    target_skill_node_id: Optional[UUID] = None

    @model_validator(mode="after")
    def drill_pair(self):
        if (self.drill_index is None) != (self.target_skill_node_id is None):
            raise ValueError("drill_index and target_skill_node_id must be provided together or both None")
        return self
```

**Backward compat:** Existing clients that POST without drill_index/target_skill_node_id continue to work unchanged — the fields default to None and the existing whole-song write path fires.

Confidence: **HIGH**. All patterns already exist in-repo (nullable-column additions in migrations 0003/0004; ORM model comment discipline in `UserSession`; SQL clamp + defense-in-depth filter in the sessions handler).

## Q3 — Rating aggregation policy

CONTEXT.md's recommended default: *"keep song-level rating for now (backward compat) but scale its mastery write DOWN when drill ratings exist"*. This works but adds a scaling factor. Below is a decision matrix.

### Options

| Option | Description | Deterministic-writes (D-05) compat | Complexity | UX legibility |
|--------|-------------|-------------------------------------|-----------|---------------|
| **A. Drill-primary, no double-count (RECOMMENDED)** | If any drill for song X is rated today, disable the song-level rating UI. If the song-level rating was submitted first, still allow drill ratings — but only the drill ratings write (song rating is a no-op for mastery purposes if drills follow). | ✅ Simple. No scaling factors. | Low. One CHECK in `submit_rating`. | High. UI clearly says "rate the drills you did; the whole-song rating is optional." |
| **B. Both write additively** | Every rating adds its full shift to affected skill_nodes. If user rates 3 drills and the song, each attached skill_node could get +0.05 four times. | ❌ Breaks D-08 additive shifts — a single day can now push a skill_node's mastery by +0.6 (4× thats_what_im_looking_for). | Low code, high semantic risk. | Low. Users don't understand why one "great" day pushed mastery so far. |
| **C. Drill ratings replace song rating (breaking)** | Remove song-level rating entirely in 4.1. All ratings are per-drill. | ✅ Cleanest. | Medium. UI rework + AlreadyRatedCard changes. | Medium. Breaks users' existing mental model. |
| **D. Song rating scaled down when drills exist** | Song rating shift ÷ (1 + drill_count_today) or similar. | ✅ Deterministic if the formula is fixed. | Medium. Requires read of today's drill count inside the transaction. | Low. Users have no way to understand the scaling. |

### RECOMMENDED: Option A — Drill-primary, no double-count

**Client-side enforcement (primary):**
- On breakdown screen: if `today.rated_drill_indices` includes any drill for the current song, hide/gray the RatingPills at the bottom of the whole-song view.
- If no drills rated yet: whole-song RatingPills active as today.
- After the FIRST drill rating for a song: whole-song RatingPills disabled with copy: *"Drills rated. The song-level rating is off — trust the drills."* (Fletcher voice; the planner can tune copy.)

**Server-side enforcement (defense in depth):**
```python
# In submit_rating, when body.drill_index is None (song rating):
if body.drill_index is None:
    existing_drill_ratings = await db.scalar(
        select(func.count(UserSession.id)).where(
            UserSession.user_id == user_id,
            UserSession.song_id == body.song_id,
            UserSession.local_calendar_day == local_day,
            UserSession.drill_index.isnot(None),
            UserSession.is_reroll_marker == False,
        )
    )
    if existing_drill_ratings > 0:
        raise HTTPException(
            status_code=409,
            detail="Song rating disabled — drill ratings already recorded for today.",
        )
```

**Why not the CONTEXT.md default (scaled-down):** Scaling is defensible in isolation but adds a math surface that has to be explained in RUNBOOK + tested + verified. Option A is one integer check + one UI branch. If real-world usage shows users WANT the whole-song rating alongside drills, adding scaling later is trivial — but adding scaling now with no signal is over-engineering.

**Trade-off acknowledged:** Option A gives up the "confirmation signal" from a song rating on top of drill ratings. Given that the drills exist specifically because the whole-song rating is too coarse, losing the coarse signal when the fine-grained signal exists is the *feature*, not a regression.

Confidence: **MEDIUM**. Reasoning is sound but this is a UX judgment call — planner should validate against Fletcher voice + surface to user for gut-check.

## Q4 — Cost estimation

### Current baseline (Sonnet 4.6 breakdown call)

Sonnet 4.6 pricing: **$3.00 / 1M input tokens, $15.00 / 1M output tokens** ([Anthropic pricing docs](https://platform.claude.com/docs/en/about-claude/pricing), [devtk.ai model card](https://devtk.ai/en/models/claude-sonnet-4-6/)).

**Current breakdown call token profile (estimated from `server/app/ai/breakdown.py`):**

- SYSTEM_PROMPT: ~1,200 tokens (rough estimate — SYSTEM_PROMPT is currently ~90 lines of guidance including the TUNING block).
- User message: ~50-100 tokens (song title/artist/skill list/user_level).
- Tool schema (`_TOOL_DEF` = `Breakdown.model_json_schema()`): ~800-1,200 tokens (Tab + Measure + Beat + Note + Chord + ChordPosition + TechniqueNote all serialized).
- **Total input:** ~2,100-2,500 tokens per call → **$0.0063-$0.0075 per call.**
- Output: 3-5 technique_notes + 4-8 measures of tab + chord diagrams ≈ 2,000-4,000 output tokens → **$0.030-$0.060 per call.**

**Current per-call cost: ~$0.036-$0.068. At 3/user/week × 4.3 weeks × 1 user = 13/mo → ~$0.47-$0.88/mo.** (This is dwarfed by onboarding calls and node verifier calls.)

### Marginal cost of adding drills

**Schema addition (input side):**
- Drill sub-model + description strings: ~400-600 tokens added to the tool schema.
- Marginal input: +400-600 tokens per call → **+$0.0012-$0.0018 per call**.

**Prompt addition (input side):**
- DRILLS block in SYSTEM_PROMPT: ~250 tokens.
- Marginal input: +250 tokens per call → **+$0.00075 per call**.

**Total input marginal: ~+$0.002-$0.003 per call.**

**Output addition:**
- 2-4 drills × ~150-350 tokens each (name + what + tab_snippet 1-2 measures + fields) = **300-1,400 output tokens added**.
- Output tab_snippet is compact (1-2 measures × 4 beats × 1-3 notes = 4-24 notes worth of JSON ≈ 100-300 tokens/snippet).
- Marginal output: +300-1,400 tokens per call → **+$0.0045-$0.021 per call**.

### Net per-call marginal cost

**+$0.007-$0.024 per breakdown call.** Round to **~$0.02 per call worst case**.

### Monthly extrapolation

At the cap (3 breakdowns/user/week) × 4.3 weeks × 1 user × $0.024 = **~$0.31/month worst case, ~$0.09/month typical**.

**Verdict: negligible.** Well inside the $20/mo Console cap. The @governed 3/user/7d cap remains the load-bearing spend control — this is the same argument that let Phase 4 ship. Drills do NOT change the cap-hit math.

### Landmines

- **`max_tokens=8192` is already set** on the `messages.create` call. Drill output stays inside this budget. If Sonnet gets loquacious on tab_snippet, worst case is truncation — the plan should include one test that verifies a synthesized-max-drills response deserializes cleanly at 8192 tokens.
- **Cache-forever contract (D-11) means drill cost is paid ONCE per song, ever.** After first generation, `breakdown_generated_at IS NOT NULL` short-circuits Sonnet. So the $0.02 marginal is truly one-shot — not per-user-view.
- **Estimator via `count_tokens` still works** — the SYSTEM_PROMPT + schema + user message go into `record_estimate` unchanged. Actuals will show slightly higher output tokens post-drills; the audit trail (`governor_calls.output_tokens_actual`) picks this up automatically.

Confidence: **HIGH** on price ($3/$15 per Anthropic docs). **MEDIUM** on token counts (estimated from source structure; actual token counts will emerge in the manual eval pass).

## Q5 — Precedent (Yousician / Fender Play / TrueFire / Justin Guitar)

Quick pass to inform framing/naming, not feature copying. Sources: [Yousician Practice Mode docs](https://support.yousician.com/hc/en-us/articles/201558362-Practice-and-Play-modes-in-guitar), [Yousician best-way-to-practice](https://support.yousician.com/hc/en-us/articles/206912609-The-best-way-to-practice-guitar), [Yousician exercise names](https://support.yousician.com/hc/en-us/articles/360001819378-What-the-exercise-names-mean), [TrueFire Song Learning System](https://blog.truefire.com/announcements/truefire-takes-song-lessons-to-the-next-level/), [Guitar World Fender Play vs Yousician](https://www.guitarworld.com/features/fender-play-vs-yousician), [TrueFire practice methodology](https://blog.truefire.com/guitar-lessons/practice-smart-record-review-refine-guitar).

**Observations:**

- **Yousician's "Practice Mode"** ships slider-controlled section loops on songs. Guitar players already understand "loop this hard bar, drill it, then rejoin the song." Fletcher's drill card + Start button lands in this same mental model. The word **loop** is the industry-idiom term; **drill** is Fletcher's synonym.
- **Yousician exercise naming** uses `basic` (simplified) vs. `main` (core essence). Fletcher's `song_specific: bool` is a cleaner two-state version of the same distinction — foundational technique vs. song-in-context drill. Don't invent new vocab; `song_specific` is a good schema field name but the UI can borrow **"For this song"** and **"Any song"** as user-facing labels.
- **Fender Play uses short, repeating drills to build endurance.** The pattern is "drill until it clicks" — matches Fletcher's rep counter + rating exit. The Fender Play "sustained execution" framing supports Fletcher's rep-count-then-rate flow better than any alternative.
- **TrueFire's "Record → Review → Refine → Repeat" loop** is close to Fletcher's tempo ladder (start → target → rate) but at a higher level. Fletcher's mechanic is a simpler subset — no video, no recording — and that's OK. **Do not overcomplicate 4.1** to match TrueFire's fidelity.
- **Justin Guitar's app** ([App Store listing](https://apps.apple.com/US/app/id1176125504)) uses lesson-based practice tracking with per-item ratings. Justin's mental model is "check off the lesson"; Fletcher's is "rate the drill." Fletcher's 3-choice pill (unlocked / getting closer / not my tempo) is more nuanced than a checkbox and closer to how a teacher would grade a student — a differentiation to lean into in Fletcher voice copy.

**Naming recommendations for planner:**
- Section header on breakdown screen: **DRILLS** (uppercase, matches existing HOW TO PLAY IT / TAB / CHORDS section labels).
- Per-drill card title area: the drill's `name` (Sonnet-authored, Fletcher voice).
- Drill card subtitle: **"For this song"** / **"Any song"** (from `song_specific`).
- Start button: **"Start drill"** (or **"Start"** if space is tight).
- Focused-drill rep counter button: **"Done one rep"** (already in CONTEXT.md; on-voice).
- Tempo ladder advance: **"Push to next tempo →"** (already in CONTEXT.md; on-voice).
- Rating exit: reuse existing 3-choice pill — do NOT invent new rating vocab.

Confidence: **MEDIUM**. Precedent is real but 4.1's design decisions are already locked in CONTEXT.md; this section is naming/framing polish, not architecture guidance.

## Landmines catalog (across all questions)

1. **Sonnet lazily slicing the main tab into `tab_snippet`.** Mitigated by explicit BAD example in SYSTEM_PROMPT + `description` on the field. Manual eval loop is the last line of defense — this is the single most likely quality gap.
2. **Sonnet hallucinating `target_skill_temp_id` values.** Mitigated by explicit prompt constraint ("MUST be one of the ids in the user message") + Pydantic validation could fail on unknown ids. Recommend adding a `@field_validator` on Drill.target_skill_temp_id that checks against the passed-in target_skill_temp_ids context — or accept it and log warnings without failing (Sonnet-authored ids that don't match should NOT crash a whole breakdown).
3. **Sonnet emitting 0 or 1 drill despite `min_items: 2`.** JSON Schema violations at Anthropic's tool_use surface manifest as `ValidationError` when Pydantic parses. Wrap in a try/except that logs the violation and treats it as a soft failure (return the breakdown without drills, don't 500 the endpoint). Users see tab/chords/technique_notes as before.
4. **Migration 0005 idempotency-index dropped-and-recreated with `COALESCE`.** Postgres partial-unique indexes support expression indexes on `COALESCE(col, sentinel)`. Verify in a spike test before the plan locks — see §Q2. If Postgres version quirks reject this, fall back to two separate partial indexes (one for `drill_index IS NULL`, one for `drill_index IS NOT NULL`).
5. **`Breakdown.model_json_schema()` order sensitivity.** Sonnet has occasionally been observed to respect field ORDER in the schema for output ordering. If drills should ORDER easiest→hardest (per CONTEXT.md), the SYSTEM_PROMPT instruction is the enforcement mechanism, NOT the Pydantic field position. Do not rely on schema field order for semantic ordering.
6. **Cached breakdowns from pre-4.1 lack the `drills` field.** Pydantic's default `drills: list[Drill] = []` handles this on the server side. Mobile must handle absent-or-empty drills gracefully — hide the DRILLS section, don't render an empty state. CONTEXT.md's Grace-B/C null-guard pattern applies.
7. **Ordering vs. drill_index integrity.** If Sonnet re-orders drills between two calls for the same song (cache-forever prevents this in prod, but during dev regen this can happen), `drill_index=2` might refer to different drills. Cache-forever contract (D-11) is what protects this; the plan must ensure that any admin-facing "regen breakdown" tool ALSO invalidates existing drill_ratings for the affected song, OR blocks regen if drill_ratings exist.

## Open Questions for the Planner

1. **Do we need a `@field_validator` that rejects Sonnet-hallucinated `target_skill_temp_id`?** Or log-warn-and-accept? Trade-off between strict correctness and shipping a usable drill even when Sonnet mis-tags one.
2. **When the user completes all drills but doesn't submit the whole-song rating, do we render an implicit "song rated" state on Today?** Or does the AlreadyRatedCard only appear after an explicit song-level rating? UX call.
3. **Manual eval loop — where does it live?** Recommend: a Wave 0 test file (`server/tests/test_drill_eval.py`) that regenerates 3 hand-picked songs' breakdowns against the LIVE Sonnet API in a marked test (skipped in CI by default) and prints the drill JSON for human review. This is a diagnostic, not a pass/fail gate — planner should slot it as a manual verification step in the last wave before shipping.
4. **Sparse skill graph interaction.** Task #18 flagged only 5 leaf skill_nodes exist. If Sonnet targets the same 5 leaves across all songs' drills, the mastery signal is diluted. Recommend: run the manual eval loop AFTER Task #18 (or in parallel) so drill quality assessment reflects a healthy graph.
