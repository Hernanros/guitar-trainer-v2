## apiFetch (mobile/src/api/apiClient.ts)
```
export async function apiFetch<T>(path: string, init?: RequestInit): Promise<T>
```
- Prepends EXPO_PUBLIC_API_URL, injects X-User-ID + X-Timezone-Offset.
- Throws `new Error('HTTP ${status} ${method} ${path}')` on non-2xx.
  IMPORTANT: apiFetch does NOT currently include the response body in the error
  message. The server sends {code: 'BREAKDOWN_CAPPED', ...} in the 429 body, but
  the mobile error message only carries the status. Error-code parsing on the
  mobile side must therefore key on HTTP status ("HTTP 429" → BREAKDOWN_CAPPED,
  "HTTP 503" → FLETCHER_OUT). This matches the existing pattern in
  breakdown/[songId].tsx lines 119-124 and the "for future use" handleBreakdownError
  at line 94-106 (which already checks both `429` and `BREAKDOWN_CAPPED` strings).

## Server endpoint contract (server/app/api/v1/breakdowns.py)
- GET /api/v1/songs/{song_id}/breakdown

- 429 → BREAKDOWN_CAPPED (per-user 3/7d cap)
